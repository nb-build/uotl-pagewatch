Customer Account, Job(Child Account), and Address Sync

Each night a one-way sync of all accounts, Jobs(child accounts in EvoX), and Addresses is pulled from Spruce customers tables and will create or update customers on EvolutionX. By default, these syncs are scheduled to run overnight to minimize any potential impact on your site’s performance during peak usage hours.

👍 Important: Any Account or Address in EvoX that has an Account code and Seller reference will be updated by the sync process. Any existing data will be overwritten with the Spruce data, as Spruce is the owner of those records.

You can also trigger a one-way sync of all accounts and child accounts from the ECI Spruce ERP App Store in EvolutionX. The duration of a sync depends on the volume of data being transferred. Larger data sets may take several hours to complete, while smaller syncs may finish more quickly. It’s recommended to plan for a few hours for larger syncs to ensure smooth operations.

Invoice Payments - Three Types of Spruce Posting Accounts

Using Spruce, Customers have many choices for paying their charge accounts. They can pay all their bills monthly in one payment, they can pay monthly by job, they can pay monthly by invoice and/or job, and they can pay by invoice with special discount terms for early payment. Each of these posting account types can be broken down by account or job:

​

Balance Forward: These accounts make bulk payments against the account or by job. Accounts that pay within a certain time, get a discount.

Open Item: These accounts make payments by invoice and collectively get a discount if they pay by a certain date. Invoices can be grouped by job.

Open Item (Terms): These accounts make payments by invoice only, and the amount of discount applied depends on the date the individual invoice is paid.

ERP Sales Code

👍 Important: Please note that this feature requires Spruce version 33 or later.

The Sales Branch Code in Spruce is an order-level field used primarily for tracking purposes, such as attributing sales commissions. This field is independent from both the order branch and the customer branch code. EvolutionX now supports sending this value when creating orders in Spruce by resolving it dynamically during checkout using a structured fallback approach.

During checkout, EvolutionX first retrieves the customer account record from Spruce. If a Sales Branch Code is defined on the customer record, that value is used directly and included in the order sent to Spruce. This ensures that any customer-specific configuration in Spruce takes priority. This value is not stored in EvolutionX which ensures that the most up-to-date value is always used.

If the customer record does not contain a Sales Branch Code, EvolutionX falls back to a new field introduced on the EvolutionX Branch configuration called ERP Sales Code. This allows businesses to define a default sales code at the branch level when customer-specific data is not available.

If the Branch ERP Sales Code is also not populated, EvolutionX performs a final fallback to a new ERP Sales Code field configured at the store level in EvolutionX Store Settings. This provides a global default to ensure a value can still be sent when neither the customer nor branch has one defined.

If no value is found across any of these three sources (customer, branch, or store), the Sales Branch Code is simply not included in the order sent to Spruce.

Tax Method

The Tax Method setting determines which tax source is used during checkout for delivery and collection orders.

By default, the integration uses Spruce tax code and rates for all orders. This means Spruce remains the source of truth for tax calculation on both delivery and collection orders.

To support stores that require more flexibility, the following additional options are available:

Override Spruce tax for all delivery orders

Delivery orders use store taxes during checkout.

Collection orders continue to use Spruce taxes.

When store taxes are used for delivery orders, the Override Tax Code value is sent with the order.

Override Spruce tax for Orders with New Addresses

For delivery orders, EvolutionX checks if the shipping address has a seller reference.

If the address does not have a seller reference, store taxes are used during checkout.

If the address does have a seller reference, Spruce taxes are used during checkout.

Collection orders always use Spruce taxes.

When store taxes are used, the Override Tax Code value is sent with the order.

👍 Important: The Override Tax Code field is always shown in the app settings and is used whenever the selected tax method applies store taxes instead of Spruce taxes.

Address State Field Mapping

This setting allows you to choose which field in Spruce should be used as the Address State value in EvolutionX. This provides more flexibility for managing delivery rules if you prefer or need to use the Delivery Point data as the primary identifier for an address location.

Go to the ECI Spruce ERP app settings and locate the Address State Field Mapping dropdown to configure your preference:

Use Spruce State Field (Default): The standard Spruce State field is mapped directly to the EvolutionX State field.

Use Spruce Delivery Point Field as State value: If the Delivery Point field in Spruce contains a value, it will be used as the State value. If the Delivery Point is empty, the system defaults to using the standard Spruce State field.

How it works

The mapping preference applies to the following synchronization processes:

Nightly Scheduled Sync: Addresses are updated during the nightly sync if the associated account has also been updated in Spruce.

Manual Account Sync: You can force an update of all addresses for a specific account by triggering a manual sync from the App Store settings.

Checkout Sync: When a user proceeds to the checkout, EvolutionX always synchronizes the address data from Spruce.

👍 Important: This setting only affects how EvolutionX reads data from Spruce. When EvolutionX sends an order (Order Sync), Spruce accepts any state value provided in the order address, so no changes are made to the order processing logic.

Add-on SKU Description Truncation

In Spruce, Add-on SKU descriptions are limited to 32 characters. If the description wraps to a second line within Spruce, only the first line (up to 32 characters) will be visible in EvolutionX. As a result, longer descriptions may appear cut off in EvolutionX and Spruce documents.

Why did a payment appear as a discrepancy in EvoX when the return had already been processed?

One of the reasons of this behavior is that the charge returns for the transactions in question were processed in Spruce but had not yet been posted. In Spruce, a return must be posted for it to be fully recognized. Until then, it remains in an "Open Credit" status.

Product shows "Out of stock" in EvolutionX but has inventory in Spruce

If you have one or more products that show as Out of Stock in EvolutionX, even though they have inventory in Spruce, confirm that both the product and the branch are eCommerce enabled in Spruce.

When EvolutionX requests available quantities, if either the branch or the product is not enabled for eCommerce, Spruce will not return any inventory data, resulting in the Out of Stock message, even if there is stock available.

Check Spruce settings to ensure both are correctly enabled for eCommerce.

UOM mismatch (Evo X --> Spruce) can also cause items to show the incorrect/outdated stock. For example, Evo X displays an items UOM as "EA" while Spruce shows "PAL".

Finance Charges

Can I require customers to pay finance charges first?

Yes. You can require customers to pay their finance charges first by enabling the appropriate setting in Spruce. In the Spruce back office, navigate to:

​Parameter Settings > Receivables > Posting Options, then select “Pay Finance Charges First.”

If this setting is not enabled, finance charges will still appear on customer accounts; however, customers can choose not to pay them.

Can finance charges be managed on a per-customer basis?

No. This setting is applied globally. Once enabled, it affects all customers and cannot be configured individually per customer.

Why did Spruce/EvolutionX show a payment as "successful" when the ACH actually failed?

Spruce imports ACH transactions as it receives a successful processor response and applies them to the account (it treats ACH like a credit‑card transaction in the UI). ACH settlement, however, is asynchronous (typically 3–5 business days) and can later be returned (NSF, wrong account, etc.). That creates the apparent “disconnect”: the payment was accepted by the processor/ODFI and posted in Spruce/EvoX, but the funds never settled to the merchant bank account.

Spruce’s official guidance on ACH handling, settlement timing, returns, daily reconciliation, and the exact procedures above: Spruce — Setting up and Managing ACH Payments
